01 — The problem

Public data is not usable data

Chicago Marathon results are published edition by edition, on separate pages, with formatting that shifts over the years. There is plenty of data available and almost no analysis possible: you cannot answer "did the elite field get faster over the last decade?" without first building the base that supports the question.

The goal was not a pretty chart. It was the opposite of what portfolios usually show: spending the time where the work actually is — ingestion, standardisation, identity resolution and modelling — so that the analysis layer became trivial and, above all, trustworthy.

As a success criterion, I decided the final dataset should stand on its own and that anyone should be able to redo the analyses from it — which is why it was published as an open resource under the ODbL licence.

02 — The data

Source, volume and what was broken

The consolidated base holds 931,958 finisher records across 25 editions between 2000 and 2025 — there was no race in 2020, cancelled due to the pandemic. I joined it with a race-day weather table, since start-line temperature, humidity and wind explain much of the variation in finish times between editions.

04 — Engineering

The four decisions holding the model up

1. Deterministic MD5 key for athlete identity

There is no stable athlete identifier across editions: bib numbers change every year and names vary in casing and accents. An incremental IDENTITY would break traceability on every reload.

The fix was a deterministic MD5 hash key derived from the athlete's normalised attributes. The same input always yields the same key, which makes the pipeline idempotent: a full reprocess produces identical keys, and partial reloads never duplicate the dimension.

2. Country code standardisation (ISO / IOC)

The source mixes ISO 3166 and IOC codes, which conflict: Germany is DEU in ISO and GER in IOC; Switzerland is CHE versus SUI. Without normalisation the same country appears as two rows in any nationality aggregation — and every "who dominates the top" analysis would be wrong from the start.

3. Bib-number collision across genders

In some editions the same bib number appears in both the men's and women's races. Treating the bib as a natural key would merge two different athletes into one. Including gender in the resolution key removed the collision.

4. Fault-tolerant time conversion

Times arrive as text in mixed formats, and some records lack the half-marathon split. Strict casting would abort the whole load over a handful of rows. I chose tolerant conversion — an invalid row becomes null and is isolated rather than killing the process — and stored times as integer seconds, which allows mean, standard deviation and differences without the pitfalls of aggregating temporal types.

SQL · tolerant conversion and Z-score normalisation T-SQL 
-- Performance relative to its own edition: normalising by the year's
-- standard deviation makes hot and cold years comparable.
WITH stats_year AS (
    SELECT Ano,
           AVG(CAST(TempoFullSegundos AS FLOAT)) AS MeanSec,
           STDEV(CAST(TempoFullSegundos AS FLOAT)) AS StdSec
    FROM   chicago.v_chicago_tempos
    WHERE  TempoFullSegundos IS NOT NULL
    GROUP BY Ano
)
SELECT t.Ano, t.Nome, t.Pais,
       (t.TempoFullSegundos - s.MeanSec) / NULLIF(s.StdSec, 0) AS ZScore
FROM   chicago.v_chicago_tempos t
JOIN   stats_year s ON t.Ano = s.Ano
ORDER BY ZScore ASC;   -- lowest Z = most exceptional performances

05 — Analysis

The questions the model can now answer

17 validated analyses, written in SQL with CTEs and window functions over the dimensional model.

  • Did the elite field get faster? (Top 10 average per edition)
  • How many runners break time milestones — sub-2:10, sub-3:00, sub-4:00 — each year?
  • What is the average finish gap between genders, and how has it evolved?
  • Which countries place the most athletes on the podium and in each edition's Top 100?
  • What is the probability of going sub-3:00 by age band and gender?
  • How does race-day weather relate to the edition's average finish time?
  • Who runs a negative split — a faster second half than first?
  • How have Brazilian participation and performance evolved?
  • Which athletes ran every edition in the window?

08 — Lessons learned

What I would do differently

Modelling before analysing saves more time than it seems. My first queries ran straight against the raw table, and every new question meant repeating the same cleaning. After the star schema, analyses that took an afternoon took minutes — and, more importantly, started agreeing with each other.

Deterministic keys are an architecture decision, not a detail. Swapping the incremental identifier for a reproducible hash is what made the pipeline safe to re-run. It is the same principle as a chart of accounts: the identifier must mean the same thing on every reload.

Data quality is a domain problem, not a code problem. Noticing that ISO and IOC coexisted in the country column did not come from an automated test — it came from checking a total that did not add up. That is exactly the reflex accounting reconciliation trains: distrust the number that looks right.

What I would change: write data-quality tests from the first load — record counts per edition, accepted value domains for country and gender, plausible time ranges — instead of discovering the problems during analysis. I would also version the normalisation rules as configuration data rather than embedding them in the transformation.
